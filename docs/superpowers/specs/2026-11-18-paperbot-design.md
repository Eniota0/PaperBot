# PaperBot — Design

Date: 2026-11-18
Status: approved 2026-11-18

## 1. Intent

A Discord bot for **technology watch** over Hugging Face Daily Papers.
Each day it takes the papers featured on HF Daily Papers **exactly 3 days
earlier (UTC date)** — the delay lets upvotes settle — sorts them into a fixed
set of categories, ranks them, and posts a digest to Discord. From the digest,
a user can pick a category from a menu and receive a **PDF** with, for every
paper in that category: a summary, practical use cases, and what is new.

Personal project today (runs on the owner's PC), but meant to grow into
something a community server or a company could use. So it should be clean,
configurable, multi-server-capable, and easy to move to a server later.

## 2. Goals

- Daily, automatic digest of HF Daily Papers for date D = today(UTC) − 3 days.
- Categorisation into a fixed, configurable list of categories, decided by an LLM.
- Ranking per category by upvotes, with a bonus for "trusted" authors.
- Per-paper enrichment: summary, use cases, what's new — generated by a
  **local LLM via Ollama** (owner has an RTX 3060, no API key).
- Digest posted as one message per category; a dropdown lets users get a PDF of
  all enriched papers for one category.
- Catch-up: when the bot starts, it processes and posts any digests missed
  while the PC was off.

## 3. Non-goals (for now)

- Reading full paper PDFs (only abstract + HF metadata are fed to the LLM).
- High availability: it's fine that nothing happens while the PC is off
  (beyond catch-up on next start).
- Web dashboard, user accounts, per-user preferences.
- Paid LLM APIs (but the LLM layer must be swappable — see §6.4).

## 4. Anti-goals (would be a failure even if it "works")

- Noisy or messy output that wouldn't be acceptable in a community/company
  server (walls of text, broken formatting, unstable categories day to day).
- Hard-coding things a future community/company would want to change
  (categories, schedule, channel, model, ranking weights).
- Making the user wait minutes after clicking the menu (enrichment must be
  done ahead of time).

## 5. Constraints

- Runs on the owner's PC (RTX 3060, 12 GB VRAM). OS not yet confirmed —
  must work on Windows and Linux.
- Python. Single process (approach A, below).
- Data source: HF public API, `GET https://huggingface.co/api/daily_papers?date=YYYY-MM-DD`
  (returns papers with arXiv id, title, abstract, authors — some linked to HF
  user accounts — upvotes, and sometimes `ai_summary` / `ai_keywords`).
  Builder must verify the exact response shape against the live API; it could
  not be reached from the design environment.
- Local LLM via Ollama HTTP API. Default model: a 7–8B instruct model (e.g.
  Qwen2.5 7B / Llama 3.1 8B); configurable.
- Discord bot via `discord.py` (needs to be online to answer menu interactions).
- All output (digest, summaries, PDF) is in **English**.
- Scale: one bot instance, at most ~2 Discord servers, all sharing the same
  categories, ranking and enrichment. Only the target channel differs per server.

## 6. Approaches considered

- **A. One Python program (chosen).** A discord.py bot with an internal daily
  scheduler that runs the pipeline (fetch → categorise → enrich → rank → store)
  and posts the digest; the same bot serves the dropdown and builds PDFs. The
  pipeline is a separate module, also runnable from the command line.
  Chosen because the owner only has to start one thing, it fits "runs when my
  PC is on", and it moves to a server unchanged.
- **B. Two programs** (pipeline started by Task Scheduler/cron + always-on bot).
  More decoupled but two things to run; only pays off on a shared server.
  The module split in A leaves this open for later.
- **C. Same as A in TypeScript/discord.js.** Rejected: Python has the better
  ecosystem for the ML/PDF/HF/Ollama parts.

## 7. Design

### 7.1 Components

```
paperbot/
  config      – loads config.yaml + .env (secrets)
  hf_client   – fetches daily papers for a date
  storage     – SQLite (papers, authors, enrichments, runs, guild settings)
  llm         – LLM provider interface + Ollama implementation
  categorize  – assigns one category per paper (LLM)
  enrich      – summary / use cases / what's new per paper (LLM)
  ranking     – score computation, author trust
  pipeline    – orchestrates one date end to end; idempotent
  pdf         – renders a category PDF
  bot         – Discord client, scheduler, catch-up, digest posting, menu
  __main__    – CLI: `bot`, `run --date`, `backfill --days N`
```

### 7.2 Daily flow

1. Scheduler fires once a day at a configured UTC time (default 08:00 UTC).
2. Target date D = today(UTC) − 3 days.
3. Pipeline for D (skips steps already done, so re-runs are safe):
   1. Fetch papers for D from HF; upsert into DB (votes refreshed).
   2. Categorise each paper not yet categorised.
   3. Enrich each paper not yet enriched.
   4. Compute scores and ranks.
4. Post digest for D to every configured channel (if not already posted there).

**Catch-up** *(builder-check answers; designer's calls)*:
- Posting is tracked **per channel** (table of (channel, date) posted).
- On startup, for each configured channel, find dates between its last posted
  date + 1 and today−3; run the pipeline for those dates (once, shared) and post
  them in chronological order.
- Cap at `catchup_max_days` (default 7): after a longer absence, only the **most
  recent** 7 missed dates are posted; older ones are skipped.
- A **fresh install** posts only today−3 (no backlog).
- A **newly added channel** (`/paperbot setchannel`) gets nothing retroactively;
  its first digest is the next scheduled run.
- A date for which HF returns no papers is marked done and nothing is posted.
- The pipeline (HTTP + LLM calls) must not block the Discord event loop: run it
  in a worker thread or use async clients.

### 7.3 Categories

Fixed list in `config.yaml`, each with a name, emoji and one-line description
(the description is given to the LLM to disambiguate). Default:

LLMs & Reasoning · Agents · Multimodal / Vision-Language · Computer Vision ·
Image & Video Generation · Audio & Speech · Robotics & Embodied AI ·
Efficiency & Inference · Training & Data · Safety & Alignment ·
Benchmarks & Evaluation · Other

The LLM gets title + abstract (+ HF `ai_keywords` if present) and must return
exactly one category name from the list (structured JSON output via Ollama's
`format` option). Invalid/unknown answers → retry once, then "Other".
A paper's category is stored and never recomputed unless forced.

### 7.4 Enrichment

For each paper the LLM produces JSON with:
- `summary` – 3–5 sentences, plain language.
- `use_cases` – 2–4 bullet points of practical applications.
- `whats_new` – 1–3 bullet points on the novelty vs. prior work.

Input: title, abstract, HF `ai_summary` if present. Output is validated; one
retry on invalid JSON; on second failure, store a fallback (abstract as
summary, empty lists) and flag it so the PDF shows "enrichment unavailable".
Prompts live in files so they can be tuned without code changes.

### 7.5 Ranking and author trust

- Only authors **linked to an HF user account** are considered for trust;
  others are ignored (no name matching).
- Author record: HF username → history of their papers in our DB with upvotes.
- **Author trust score** = number of their *previous* papers (strictly before D)
  that reached at least `trust_vote_threshold` upvotes (default 50), capped at
  `trust_cap` (default 5).
- **Paper trust** = max author trust among its HF-linked authors.
- **Paper score** = `upvotes × (1 + trust_weight × paper_trust)`,
  default `trust_weight` = 0.05 (so max +25%). All values in config.
- Papers ranked by score within their category. Categories are ordered in the
  digest by total upvotes of their papers (most active first); empty
  categories are omitted.
- A paper gets a ⭐ marker in the digest when paper_trust > 0.
- **Cold start:** `backfill --days N` (default 90) fetches past days' metadata
  only (no LLM calls) to seed author history. Run automatically on first start
  if the DB is empty.

### 7.6 Discord output

- Per date: a header message ("📚 HF Papers — 2026-11-15 · 34 papers"), then
  one embed per non-empty category listing its papers:
  `rank. ▲votes  Title (link to HF paper page)  ⭐?`, top N per category
  (default 10, config) with "+k more in PDF" if truncated.
- A final message with a **select menu** of the day's categories. Choosing one
  makes the bot reply with the PDF for (date, category) as an attachment.
  Reply is **ephemeral** (only visible to the clicker) to keep the channel clean.
  Menu must keep working after a bot restart (persistent view; custom_id encodes
  the date).
- Long titles are truncated to fit Discord embed limits.
- Multi-server (≤ ~2 servers, one shared pipeline): target channel per guild stored in DB, set with a slash
  command `/paperbot setchannel` (admin only). A default channel id in config
  for the personal setup.

### 7.7 PDF

One PDF per (date, category), generated on demand from stored data (fast) and
cached on disk. Content: cover line (category, date, paper count), then per
paper in rank order: title, authors, votes, links (HF page, arXiv), summary,
use cases, what's new. Embed a Unicode TTF font (e.g. DejaVu Sans) so author names with accents or
non-Latin characters render. Library: builder's choice among pure-Python options
that install cleanly on Windows (e.g. ReportLab or fpdf2) — avoid ones that
need system libraries.

### 7.8 Config and secrets

- `.env`: `DISCORD_TOKEN`.
- `config.yaml`: schedule time, delay days (3), categories, ranking weights,
  top N, catch-up cap, Ollama URL + model, default channel id.
- `config.example.yaml` + `.env.example` committed; real ones git-ignored.

### 7.9 LLM abstraction

`LLMProvider` interface with `complete_json(prompt, schema) -> dict`. Ship the
Ollama implementation only; adding Claude/OpenAI later is a new class plus a
config switch. Calls are sequential (one GPU); ~30–50 papers × 2 calls/day is
expected to take a few minutes on a 3060.

### 7.10 Errors and logging

- HF unreachable → retry with backoff; if still failing, skip that date and
  retry it on next schedule/start (it stays "not posted").
- Ollama unreachable → pipeline aborts for that date before posting, logs a
  clear message ("is Ollama running?").
- Logging to console + rotating file.

### 7.11 Testing

- Unit tests for ranking/trust, date logic (UTC, D−3, catch-up range),
  LLM output validation, digest formatting (limits), PDF generation smoke test.
- HF client tested against recorded JSON fixtures.
- LLM mocked in tests; one optional manual integration test against Ollama.

- How the scheduler is implemented (discord.py `tasks.loop` or similar).
